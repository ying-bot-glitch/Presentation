Node 4 · 数据预处理（关键）

这一步决定了 LLM 看到什么。裁剪不当 → 内容太多 → token 爆炸 + 摘要质量下降。

A.4
Prepare Data
Code · JavaScript
把两个 feed 合并、按点赞数过滤低质量推文、控制每个 builder 最多 2 条、裁剪播客 transcript 到 2500 字。
输入变量
x_body
String
← Fetch X Feed / body
pod_body
String
← Fetch Podcast Feed / body
核心代码
function main({ x_body, pod_body }) {
  const xData = JSON.parse(x_body);
  const podData = JSON.parse(pod_body);

  // 取前 8 位 builder，每人最多 2 条点赞过 5 的推文
  const builders = (xData.x || [])
    .filter(b => b.tweets && b.tweets.length > 0)
    .slice(0, 8)
    .map(b => ({
      name: b.name,
      bio: (b.bio || '').split('\n')[0].slice(0, 80),
      tweets: b.tweets
        .filter(t => t.likes >= 5 && t.text.length >= 30)
        .slice(0, 2)
        .map(t => ({ text: t.text, url: t.url, likes: t.likes }))
    }));

  // 取最新 1 集播客，transcript 裁到 2500 字
  const episodes = podData.podcasts || podData.episodes || [];
  const podcast = episodes[0] ? {
    title: episodes[0].title,
    transcript: (episodes[0].transcript || '').slice(0, 2500)
  } : null;

  return {
    builders_json: JSON.stringify(builders, null, 2),
    podcast_json: JSON.stringify(podcast, null, 2),
    builder_count: builders.length
  };
}

function main({ llm_text }) {

A.8
Filter Subscribers
Code · JavaScript
解码 base64、按 frequency 过滤。daily 用户每天发，weekly 用户只在周一发。
function main({ file_response }) {
  const fileData = JSON.parse(file_response);
  const decoded = Buffer.from(fileData.content.replace(/\n/g, ''), 'base64').toString();
  const data = JSON.parse(decoded);

  const today = new Date();
  const isMonday = today.getDay() === 1;

  const toSend = data.subscribers.filter(s => {
    if (s.active !== true) return false;
    if (s.frequency === 'daily') return true;
    if (s.frequency === 'weekly' && isMonday) return true;
    return false;
  });

  return { recipients: toSend, send_count: toSend.length };
}

08 · Workflow B · Node Detail

Process Subscribers · 核心业务逻辑

Workflow B 最关键的一个节点。三件事：校验、去重、生成新文件内容。

B.3
Process Subscribers
Code · JavaScript
输入变量 · 重点
current_file
String
← Get Subscribers File / body
webhook_raw
Object
← Webhook Trigger / _webhook_raw（整个原始请求）

⚠ Dify 的 Webhook 不暴露 body.email 这种嵌套字段，只能拿到 _webhook_raw 整体，在代码里解构。

核心逻辑
function main({ current_file, webhook_raw }) {
  // 从原始 webhook 数据里提取参数
  const body = webhook_raw.body || webhook_raw || {};
  const new_email = (body.email || '').trim();
  const new_topics = (body.topics || '').trim();
  const new_frequency = (body.frequency || '').trim();

  // 解码当前文件 + 拿 SHA
  const fileData = JSON.parse(current_file);
  const sha = fileData.sha;
  const base64 = (fileData.content || '').replace(/\n/g, '');
  const subscribersData = JSON.parse(Buffer.from(base64, 'base64').toString());

  // 三道校验
  if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(new_email)) {
    return { success: false, message: '邮箱格式不正确', sha };
  }
  if (!['daily', 'weekly'].includes(new_frequency)) {
    return { success: false, message: 'frequency 必须是 daily 或 weekly', sha };
  }
  if (subscribersData.subscribers.find(s => s.email === new_email)) {
    return { success: false, message: '该邮箱已订阅', sha };
  }

  // 追加新订阅者 + 编码新内容
  subscribersData.subscribers.push({
    email: new_email.toLowerCase(),
    topics: new_topics.split(',').map(t => t.trim()),
    frequency: new_frequency,
    created_at: new Date().toISOString().split('T')[0],
    active: true
  });

  const newJson = JSON.stringify(subscribersData, null, 2);
  return {
    success: true,
    message: '订阅成功',
    sha: sha,
    new_content_base64: Buffer.from(newJson).toString('base64')
  };
}

B.5
Write to GitHub
HTTP · PUT
把新的 subscribers.json 内容提交回仓库。每次写入会产生一个 commit。
MethodPUT
URLapi.github.com/repos/{owner}/{repo}/contents/subscribers.json
HeadersAuthorization: Bearer {PAT}

{
  "message": "Add new subscriber via Dify webhook",
  "content": "{{#process_subscribers.new_content_base64#}}",

SHA 是 GitHub Contents API 的"乐观锁"机制——如果两个请求同时写入，后到的那个 SHA 会失效，请求会被拒绝。这保证了并发安全。

Service 2
EXT.2
Cloudflare Worker · CORS 代理
Edge Function
为什么需要：浏览器直接 POST 到 Dify Webhook 会被 CORS 拦截。Worker 在 Cloudflare 边缘节点转发请求，加上 CORS headers。免费版 10 万请求/天。
const CORS_HEADERS = {
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Methods': 'POST, OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type',
};

export default {
  async fetch(request) {
    // 浏览器 preflight 请求
    if (request.method === 'OPTIONS')
      return new Response(null, { headers: CORS_HEADERS });

    // 转发到 Dify webhook
    const body = await request.text();
    const r = await fetch(DIFY_WEBHOOK_URL, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json; charset=utf-8' },
      body: body,
    });

    return new Response(await r.text(), {
      status: r.status,
      headers: { ...CORS_HEADERS, 'Content-Type': 'application/json' },
    });
  }
};

11 · Pitfalls

真实踩过的坑（一）

这些不会出现在任何教程里。是实际搭出来后撞了墙才知道的事。

⚠ Pitfall · 01 · LLM thinking 污染
DeepSeek V4 Pro 默认开 Thinking，输出会被 <think> 标签包裹

第一次 LLM 节点跑完，输出多了一大段 <think>...</think> 推理过程，导致 JSON.parse 失败。token 数也飙了 4 倍、延迟 41 秒。

解决：在 Model Settings 里关闭 Thinking Mode，输出立刻变干净。延迟降到 14 秒，token 数减半。这类摘要任务根本不需要 thinking。

⚠ Pitfall · 02 · Webhook 嵌套字段无法访问
Dify 不让你选 _webhook_raw.body.email 这种嵌套路径

变量选择器里只能选 _webhook_raw（整个 Object），无法继续展开。试图手填 {{#webhook.body.email#}} 也不工作。

解决：在 Code 节点里接收 webhook_raw 整体，在代码里用 webhook_raw.body.email 解构。把嵌套访问的复杂度留在代码里，节点的 UI 只暴露顶层变量。

⚠ Pitfall · 03 · Iteration 内部变量绑定
subscriber 输入绑错节点，循环全部报 Cannot read property 'email' of undefined

在 Iteration 内部加 Code 节点时，本能地把 subscriber 绑定到 Filter Subscribers / recipients（整个数组）。结果代码拿到的是数组而不是单个对象。

解决：必须绑定到 Iteration / item（当前迭代的元素）。这个变量在选择器里有专门的 CURRENT ITERATION 分组。

⚠ Pitfall · 04 · Iteration 错误传播策略
第一次循环失败，整个 Iteration 就停了

Iteration 节点默认 Error Response Method = Terminated。这意味着 5 个订阅者只要第一个发送失败（比如 Resend 限制），后面 4 个都不会发送。

解决：改为 Continue on Error。即使部分失败，循环也会跑完所有元素。

12 · Pitfalls

真实踩过的坑（二）

⚠ Pitfall · 05 · 浏览器 CORS 拦截
前端 fetch 直接调 Dify Webhook，浏览器报 blocked by CORS policy

第一次接通前端时，PowerShell 测试 webhook 都好好的，浏览器一调就挂。Dify 的 Webhook 服务器没有为前端域名设置 CORS headers。

解决：用 Cloudflare Worker 做代理。10 行 JS 代码：接收前端请求 → 加 CORS headers → 转发到 Dify。同样适用于任何"前端 → 第三方 API"被 CORS 拦截的场景。

⚠ Pitfall · 06 · Resend 免费版收件人限制
未验证域名时，只能发到注册账号的那个邮箱

测试发到其他邮箱时 Resend 返回 403 + "You can only send testing emails to your own email address..."。这是 Resend 的反垃圾策略。

解决方案 A：买个域名（.xyz 约 ¥10/年），在 Resend 添加 + 配置 DNS records 后即可发到任意邮箱。

解决方案 B：搬到公司 Dify，用公司邮件服务发，绕过 Resend。

⚠ Pitfall · 07 · PowerShell 的 curl 不是 curl
测试时输入 curl 命令报 ParameterBindingException

在 PowerShell 里 curl 是 Invoke-WebRequest 的别名，参数语法跟 Unix 的 curl 完全不同。直接复制 Linux curl 命令会报错。

解决：用 PowerShell 原生的 Invoke-RestMethod，配合 UTF-8 编码处理中文 body：

$body = @{ email="test@x.com"; topics="AI产品" } | ConvertTo-Json
Invoke-RestMethod -Uri $url -Method POST `
  -ContentType "application/json; charset=utf-8" `
  -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
⚠ Pitfall · 08 · Schedule Trigger Test Run 是监听模式
点 Test Run 后 Workflow 一直 Listening 不执行

Schedule Trigger 的 Test Run 不像普通节点那样立刻跑，而是进入"监听模式"等定时器自然触发。如果时间没到，会一直等。

解决：暂时把 Schedule 改到当前时间后 1-2 分钟，让定时器很快自然触发；或者部分 Dify 版本支持右键节点 "Run from here"。

13 · Migration

搬迁到公司 Dify

从个人 Dify Cloud 搬到公司部署的 Dify，比想象中简单。DSL 导出导入保留了所有节点、变量、Prompt、代码。

个人 Dify Cloud · Export DSL

打开 Workflow → 右上角 ⋯ 菜单 → Export DSL。会下载一个 .yml 文件，包含整个 Workflow 的完整定义。

公司 Dify · Import DSL

Studio 首页 → Import DSL file → 上传 .yml。Workflow 立即创建好，所有节点、连线、变量绑定、代码、Prompt 全部还原。

重新配置敏感凭证

不会自动迁移的部分（这是合理的安全设计）：LLM API Key、Resend API Key、GitHub PAT。重新填入即可。

切换邮件方案 · 用公司域名发件

公司 Dify 部署在内网，可以用公司 SMTP 服务器或公司域名验证过的 Resend 账号发件。这是搬迁最大的价值——邮件能真正发到任意公司同事邮箱。

Publish · 等待第一次定时触发

记得点 Publish 按钮（而不是只 Save）。Schedule Trigger 必须 publish 才会真正按时触发。第一次定时跑成功 = 整个系统真的上线了。

关于 Dify 的能力边界

能干 / 不能干

Dify 擅长的是"短任务编排"：HTTP 调用、LLM 推理、条件判断、循环、数据转换。每个节点跑几秒到几十秒。

不擅长的是"长任务"——比如训练一个模型，或者运行一个 24 小时不停的爬虫。Dify 是事件驱动的，不是 daemon。

这恰好覆盖了 80% 的"自动化 + AI"场景。

关于"GitHub 当数据库"

非传统但好用

把 subscribers.json 放仓库里听起来不专业，但实际上：免费、可审计（每次写入有 commit）、无需运维、对小规模场景完全够用。

订阅者超过 1000 / 写入频率超过每秒 1 次时再迁数据库。在那之前，这是最快的方案。

关于自然语言生成代码

瓶颈不是 AI 能力

Vibe Coding 已经足够好。让 AI 写 React 组件、写 Worker 代码、写 Code 节点的逻辑，都不是问题。

真正的瓶颈是写出有判断力的设计 spec。Prompt 的精度决定了产出的精度。

关于这套架构的可复用性

模板已经在了

"定时抓数据 → AI 处理 → 写数据库 → 循环通知"是个万能模板。把 follow-builders 换成任何 RSS / API，把"发邮件"换成"发钉钉/企微/Slack"，整个 Workflow 几乎不用改。

这一周搭的不是一个产品，是一个工厂。
